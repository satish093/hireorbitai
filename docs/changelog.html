Realtime messaging — Phase 6New

2026-05-18

Messages now appear instantly across every open tab — no more 8-second polling wait. The same channel will power notifications, presence, and live task updates without further plumbing.

  • New persistent push channel: every signed-in browser keeps one Server-Sent Events stream open against the API. New messages, edits, and deletes arrive within ~50 ms instead of every 8 s.
  • Cross-server delivery via Postgres LISTEN/NOTIFY — no Redis, no new dependency. Each backend worker listens on its own connection; Postgres broadcasts to all workers so the recipient always gets the push regardless of which worker the sender hit.
  • Reusable infrastructure: the same publishToUser(userId, event, payload) helper will power future notifications, presence indicators, typing dots, and any other "the server needs to tell the browser something" feature without new endpoints.
  • Graceful fallback: if the stream drops mid-session, the existing 60-second sidebar poller catches anything missed during the gap. Auto-reconnect with exponential backoff (1s → 30s cap) handles network blips automatically.
  • Heartbeat every 25 s keeps proxies / load balancers from killing idle connections.
  • One operations note: the production Nginx vhost needs proxy_buffering off for the /api/realtime/stream location so SSE chunks flush as they're sent. Without it, events would batch into multi-second clumps.

Messaging — Phase 4: performance & observabilityPerformance

2026-05-17

Permission checks now run from a 30-second in-memory cache and from a unified org-relationship view, cutting messaging-route latency to near-zero on the cached path.

  • In-memory permission cache keyed by user + role. First request per 30-second window does the full hierarchy resolution; the next ~N requests in that window read from the cache instantly.
  • Self-bounded memory: cache evicts the oldest 1k entries if it ever exceeds 5k — basically free.
  • Invalidation hook exported (invalidatePermissionCache(userId)) — ready to wire into future relationship-mutation paths so changes propagate within milliseconds instead of waiting for TTL.
  • New Postgres view v_user_relationships unifies the four canonical sources (reports_to, recruiter_managers, recruiters.manager_id, consultants.recruiter_id) under one read-only shape. Symmetric — emits each relationship in both directions so a point-lookup answers reachability without an OR.
  • Defers full RLS policies to a follow-up: our single-connection-pool architecture doesn't map cleanly to per-row PostgreSQL policies. Application-level checks in the permission service remain the canonical boundary.

Messaging — Phase 3b: edit & retractNew

2026-05-17

Sender-side controls for fixing typos and deleting messages, with optimistic UI that snaps back on failure.

  • Hover any of your own messages to see ✎ Edit and ✕ Delete pills above the bubble.
  • Edit: in-place textarea. Enter saves, Esc cancels, Shift+Enter for newline. Recipients see “· edited” next to the timestamp.
  • Delete: confirm dialog → message removed for both sender and recipient. Row is soft-deleted in the DB for compliance (never hard-deleted).
  • Optimistic UI: edits and deletes apply instantly; on backend failure, the original message snaps back with a toast explaining what went wrong.
  • Edits and deletes are sender-only — atomic sender_id = caller.id check at the SQL layer means a forged id returns 404 with no oracle about whether the row exists.

Messaging — Phase 2: soft-delete & cleanupNew

2026-05-17

Schema additions + a unified directory implementation.

  • Messages now carry deleted_at and edited_at timestamps. Every API surface filters soft-deleted rows. Recipients no longer see ghost “1 unread” badges for retracted messages.
  • Partial indexes on the new columns keep performance flat — the deleted_at filter never full-scans the messages table.

  • New endpoints: PATCH /messages/:id (edit body, sender only), DELETE /messages/:id (soft-retract, sender only).

Messaging — Phase 1: closed 3 vulnerabilitiesSecurity

2026-05-17

Three direct-messaging vulnerabilities closed, with a centralized permission engine to keep future endpoints safe by default.

Closed

  • Any signed-in user could read another pair's private thread by guessing the URL. Now requires you to be in the same hierarchy or have an existing thread with the peer.
  • Any signed-in user could silently mark a stranger's messages as “read” on their own inbox. Same authorization rule now applies.
  • Any signed-in user could send a message to any other user, bypassing reporting structure. POST /messages now refuses recipients outside your scope.

Behind the scenes

  • New centralized permission service — every check (send, view thread, mark read, future features) reads the same rule set. No more drift between endpoints.
  • Denied requests now write a messages_permission_denied row to the audit log so admins can see attempts.
  • No schema changes, no breaking API changes. Existing conversations stay reachable; only new boundary-crossing attempts are blocked.

Security hardening — round 1Security

2026-05-17

Five high-impact, low-effort fixes from a full-stack audit.

  • Invitation preview email now masked (s************@gmail.com) — blocks email-harvesting via leaked tokens.
  • HSTS bumped to 1 year + includeSubDomains + preload eligibility.
  • Referrer-Policy: strict-origin-when-cross-origin so outbound links don't leak the full URL.
  • Permissions-Policy: camera, microphone, geolocation, payment, USB all denied at the browser level.
  • Per-route rate limit on AI endpoints (30 requests per 5 minutes) — prevents runaway Anthropic spend from a tight loop.
  • Postgres statement timeout (15s default) — prevents a slow query from holding a connection pool slot forever.
  • npm audit wired into CI to catch high/critical CVEs at PR time.
